# 踩过的坑与已知限制

全部是实测记录，能复现的坑都写了复现方法。

## 坑一：`CURRENT_NOW` 单位是 mA，不是文档写的 µA

**现象**：第一版界面显示 `0.0 W`，但电流字段明明是 `-1333`。

**原因**：Android 文档写单位是微安，这台联发科机器实际给毫安。按微安算是 0.0013 A，乘 4.4 V 得 0.006 W，四舍五入就是 `0.0`。

**修复**：按数值幅度判单位，不猜平台。

```kotlin
abs(rawNow) / if (abs(rawNow) >= 100_000) 1_000_000.0 else 1_000.0
```

**复现**：`adb shell dumpsys battery | grep current`，看数值量级。4 位数的是 mA，7 位数的是 µA。

## 坑二：`getIntProperty` 对不存在的属性直接抛异常

**现象**：加上属性探测日志后，应用启动即崩溃。

**原因**：`BatteryManager.getIntProperty()` 对这台机器上不存在的属性（`CURRENT_AVERAGE`、`ENERGY_COUNTER`）抛 `SecurityException`，因为它需要 `BATTERY_STATS` 系统权限。文档没强调这一点。

**修复**：每个调用单独包 `try/catch`，失败当 `Int.MIN_VALUE` 处理。

```kotlin
val rawNow = try {
    bm?.getIntProperty(BatteryManager.BATTERY_PROPERTY_CURRENT_NOW) ?: Int.MIN_VALUE
} catch (e: Throwable) {
    Int.MIN_VALUE
}
```

## 坑三：`EXTRA_VOLTAGE` 返回垃圾值 `4`

**现象**：电流读对了，电压显示 `0.00 V`。

**原因**：这台机器返回 `4`（正常应为 4400 mV 左右）。而且这不是应用读错——`adb shell dumpsys battery` 里同样显示 `voltage: 4`，**框架层本身就是坏的**，厂商没往这个字段填值。

**修复**：只采信 3000–5000 mV 区间内的值，其余按电量拟合。详见 [3-功率是怎么算出来的.md](3-功率是怎么算出来的.md)。

**影响**：功率从「精确计算」降级为「约 3% 误差的估算」。这是本项目精度天花板，无法绕过。

## 坑四：SELinux 封死 `/sys/class/power_supply`

**现象**：想读输入侧功率，`ls /sys/class/power_supply/` 直接 `Permission denied`。

**原因**：系统 SELinux 标签 `sysfs_battery_supply` 不对 `untrusted_app` 开放。国产 ROM 一律不给，Pixel 多数机型允许。

**验证方法**：

```bash
# shell 用户（adb）可以读
adb shell cat /sys/class/power_supply/usb/current_now

# 应用身份读不到
adb shell run-as app.chargescope ls /sys/class/power_supply/
# → Permission denied
```

**采用过的绕行方案，全部失败**：

| 尝试 | 结果 |
|---|---|
| `run-as` 直接读节点 | Permission denied |
| `readlink -f` 找真实设备路径再读 | 同样被拦 |
| `/proc/mtk_battery_cmd` | 不存在 |
| `/sys/devices/platform/.../oplus_mms/wired/` | 路径存在但不可读 |

**结论**：无 root 拿不到输入侧功率。这是硬限制，不是代码问题。

## 坑五：ColorOS 熄屏 14 秒后强行回收 `PARTIAL_WAKE_LOCK`

**现象**：前台服务在熄屏后采样 14–17 秒就停，服务本身还活着。

**原因**：`dumpsys power` 日志显示：

```
15:35:37.119  ACQ ChargeScope::recording (partial)
15:35:51.553  REL ChargeScope::recording
```

`ACQ` 后 14 秒被系统主动 `REL`，不是应用自己释放的。

**试过的解法**：

| 方案 | 结果 |
|---|---|
| `PARTIAL_WAKE_LOCK` | 14 秒后被回收 |
| `cmd deviceidle whitelist +包名` | 无效 |
| 前台服务 + 常驻通知 | 无效 |
| 检查进程 cgroup / 冻结状态 | 进程未被冻结，锁先没的 |

**最终决定**：删掉整个后台采样功能。用户要的是「亮屏看一眼当前功率」，不是充电日记。留一个会断的开关比没有更糟。

**顺带纠正一个判断**：我最初批评同类应用申请 6 小时唤醒锁「反而让机身更热、干扰测量」。这个批评是错的——在 ColorOS 上，唤醒锁是**必需**的，不然根本采不到数。

## 坑六：拔线后显示「未充电 · 3.5 W」

**现象**：模拟拔线后，状态显示「未充电」，下面却还是绿色的 `3.5 W`，自相矛盾。

**原因**：拔线后 `CURRENT_NOW` 仍有值，但那是**放电电流**。乘上电压得到一个看着很像充电功率的数。

**修复**：判定充电状态只看 `EXTRA_PLUGGED` 和 `EXTRA_STATUS`，不看电流符号；没在充电就显示 `-- W`。

## 坑七：功率平稳时曲线糊成一整块绿色

**现象**：功率稳定在 2.9 W 时，曲线图变成一个整块填充的绿方块，看着像渲染错误。

**原因**：纵轴从 0 开始算，最大值 `peak × 1.15`。功率平稳时数据线贴在顶部，下面的填充区全部被涂满。

**修复**：纵轴改为跟随数据范围，并保底最小跨度：

```kotlin
val span = maxOf(hi - lo, maxOf(hi * 0.3f, 0.8f))
```

这样数据平直时曲线落在中间，有波动时自动放大。

# 已知限制

按重要性排序，用之前先知道这些。

## 1. 拿不到充电头输出的功率

显示的是**进电池的功率**，比充电口输入低，比充电头标称低更多。三层关系：

```
充电头标称 80W  →  充电口输入约 63W  →  进电池（本应用显示的数）
```

每层都有损耗，差额来自充电管理芯片、屏幕、系统负载。想知道充电头真实输出，只能用硬件 USB 功率计。

## 2. 电压是推算值，功率有约 3% 误差

系统不给电压（见坑三），只能按电量查表插值。电流是精确的，电压是估的。充电过程中因极化压升，推算值会略高于真实端电压。

长按大数字可以看到当前用的电压、电流、功率原始值，自行判断。

## 3. 剩余时间是线性估算，高电量时偏乐观

把当前功率当成未来恒定值算。实际功率会随电量下降，所以 96% 时显示「20 分钟」通常比实际短。

## 4. 没有历史记录

不存数据库、不导出 CSV、没有多日对比。退到后台就停止采样，回来重新开始 60 秒窗口。

## 5. 只有亮屏时工作

见坑五。这不是省电设计，是系统不允许。

## 6. 亮屏本身会降低充电功率

这条不是缺陷，但会误导测量：你盯着屏幕读数的动作，让手机主动降了 10–20 W。想测真实峰值，插上后熄屏，过几分钟再点亮看一眼。

## 7. 按调试签名打包

不能上架、不宜转发。要正式分发需自建 keystore，见 [4-构建与安装.md](4-构建与安装.md)。

## 8. 其他品牌未验证

只在 OPPO Find X8s（联发科，Android 16）上实测过。代码按能力探测而非品牌分支，理论上 Pixel、三星、小米都该能跑，但**没有实机验证**。遇到问题，长按大数字看原始值就能定位。
