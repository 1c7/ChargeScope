# 项目结构与技术选型

## 这个应用做什么

读电池的电流，乘以电压，得到功率，显示成一个数字。全部逻辑不超过 400 行。

## 为什么用原生 Kotlin，不用 Flutter

| | 原生 Kotlin（本方案） | Flutter |
|---|---|---|
| 安装包 | 2.0 MB | 约 14 MB（引擎约 12 MB） |
| 启动到出数 | 首个 Activity 帧就有数 | 需等引擎初始化，首屏白屏 |
| 第三方依赖 | 零 | 引擎 + 插件链 |
| 跨平台收益 | —— | **本需求为零**，只有一个界面 |

界面只有一个页面：四个文本控件加一条 90dp 高的曲线。跨平台在这里没有意义，只会带来体积和一层 MethodChannel 通信延迟。

## 代码结构

| 文件 | 行数 | 职责 |
|---|---:|---|
| `ChargeSampler.kt` | 76 | 读系统电池数据、单位自适应、电压推算、剩余时间估算 |
| `MainActivity.kt` | 173 | 唯一界面。500 ms 刷新，长按弹原始读数 |
| `SparklineView.kt` | 117 | 自绘 60 秒功率曲线，含平均线 |
| `AndroidManifest.xml` | 22 | 只有一个 Activity，**无任何权限声明** |

合计 388 行。

## 运行参数

| 项目 | 值 |
|---|---|
| 采样间隔 | 500 ms |
| 曲线容量 | 120 点，即 60 秒窗口 |
| 刷新时机 | 仅 `onResume` → `onPause` 之间，退到后台立即停止 |
| 常驻服务 | 无 |
| 后台任务 | 无 |
| 网络 | 无 |
| 权限 | 无 |

## 关键设计：Activity 自己采样，不共享轮询器

有些同类应用让 Activity 和前台服务共用一个轮询器，靠引用计数启停。这种结构在 `onPause` 时很容易把另一边正在用的任务取消掉，表现为「一锁屏数据就冻结」。

本项目没有服务，只有一个 Activity 自持一个 `Handler`，`onPause` 摘掉回调，`onResume` 重新挂上。不存在两个使用者争抢同一个循环的问题。

## 为什么不做后台常驻

最初实现过前台服务加 CSV 记录，用于息屏连续采样。实测在 ColorOS 上做不到：熄屏 14 秒后系统强行回收 `PARTIAL_WAKE_LOCK`（`dumpsys power` 日志里 `ACQ` 紧接着 `REL`），加入 `deviceidle` 白名单也无效。

既然做不到，就删掉功能，而不是留一个会断的开关。详见 [5-踩过的坑与已知限制.md](5-踩过的坑与已知限制.md)。

## 为什么不去读 `/sys/class/power_supply`

读不到。系统 SELinux 标签 `sysfs_battery_supply` 不对普通应用开放，连 `ls` 目录都返回 Permission denied。只有 `adb shell`（shell 用户）能读。详见 [2-各家手机读取电池数据的差异.md](2-各家手机读取电池数据的差异.md)。
